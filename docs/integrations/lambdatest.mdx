`lambdatest()` from `@e2e-dev/lambdatest` is a
[browser provider](/browser#hosted-browsers) for
[LambdaTest](https://www.lambdatest.com). By default each worker slot gets its
own LambdaTest session for the run; `scope: 'attempt'` gives every test
attempt its own session instead. Tests and CI stay the same; the config
changes only in the target's `browser`.

## Setup

<CodeGroup>
```bash npm
npm install --save-dev @e2e-dev/lambdatest
```

```bash pnpm
pnpm add -D @e2e-dev/lambdatest
```

```bash bun
bun add -d @e2e-dev/lambdatest
```
</CodeGroup>

```ts title="e2e.config.ts"
import type { E2EConfig } from 'e2e';
import { web } from '@e2e-dev/web';
import { lambdatest } from '@e2e-dev/lambdatest';

export default {
  targets: [
    {
      name: 'lambdatest',
      engine: web({ browser: lambdatest(), viewport: null }),
      app: { url: 'https://staging.example.com' },
    },
  ],
} satisfies E2EConfig;
```

Set `LT_USERNAME` and `LT_ACCESS_KEY` in the environment `e2e run` starts in,
such as CI secrets. Each worker gets its own session, so `workers` sets how
many run at once; keep it within your LambdaTest plan's parallel sessions,
since a session beyond it waits in LambdaTest's queue.

## Options

| Option | Default | Meaning |
| ------ | ------- | ------- |
| `scope` | `'worker'` | `'worker'`: one session per worker slot for the run. `'attempt'`: a fresh session per test attempt, retries included. See [Scopes](#scopes). |
| `browserName` | `'Chrome'` | `'Chrome'` or `'MicrosoftEdge'`. The web engine attaches over CDP, so the browser must be Chromium-based. |
| `browserVersion` | `'latest'` | Any version LambdaTest offers for the platform, such as `'140'`. |
| `platform` | `'Windows 11'` | A LambdaTest desktop platform, such as `'Windows 10'` or `'macOS Sequoia'`. |
| `build` | `'e2e <run id>'` | The LambdaTest build the sessions are grouped under. |
| `route` | `'/puppeteer'` | The hub route that serves the session's CDP endpoint. See [Routes](#routes). |
| `hub` | `'cdp.lambdatest.com'` | The hub host. |
| `capabilities` | none | Further `LT:Options` capabilities, such as `video`, `network`, `console`, `idleTimeout`, `resolution`, or `tunnel` and `tunnelName` for [LambdaTest Tunnel](https://www.lambdatest.com/support/docs/testing-locally-hosted-pages/). `user` and `accessKey` always come from the environment. |

```ts
lambdatest({
  scope: 'attempt',
  platform: 'macOS Sequoia',
  build: `checkout ${process.env.GITHUB_SHA}`,
  capabilities: { video: true, network: true, idleTimeout: 300 },
})
```

## Scopes

`scope: 'worker'` keeps one session per worker slot for the whole run and
gives every attempt a new browser context in it, as a local run does: a test
never sees another test's cookies, storage, or permissions. LambdaTest shows
it as one session, named after the target and the slot, that covers every
test the worker ran.

`scope: 'attempt'` starts a session per attempt, so each test is its own
LambdaTest session, named after the target and the attempt. It costs a
session start per test and carries the limits of a
[per-attempt lease](/browser#hosted-browsers): no `headers`, `basicAuth`, or
`userAgent`, no `app.clearState()`, and no [sessions](/authentication). A
dropped connection cannot be resumed: reconnecting would start a new
LambdaTest session, so the attempt fails instead.

## Routes

A LambdaTest session starts when its CDP websocket opens, on one of the
hub's routes:

- `'/puppeteer'` (default) serves a raw CDP endpoint and works with every
  account today. LambdaTest's dashboard labels these sessions Puppeteer.
- `'/playwright-cdp'` is LambdaTest's route for Playwright's
  `connectOverCDP`. Its sessions are labelled Playwright. Use it once
  LambdaTest serves raw CDP on it for your account.

## Recordings

LambdaTest records the session's screen itself when you pass
`capabilities: { video: true }`; watch it in the LambdaTest dashboard. The
provider does not hand that recording to e2e, so an attempt that records
[video](/reference/config#video) gets the web engine's screencast of the
page, as a local run does.

## Downloads

LambdaTest's browsers save downloads on their own machines, and the provider
has no way to read them back, so `browser.waitForDownload` fails with
`ENGINE_FAILURE` naming the provider. Assert on the download link or the
request instead.

## What the provider does

- Builds the session's CDP URL with the capabilities above and returns it as
  the lease. It calls no LambdaTest API: opening the websocket starts the
  session and the engine closing it ends the session, so `release` has
  nothing to call.
- Names every session `e2e <target> <slot or attempt>` inside the build, and
  logs `LambdaTest session "<name>" in build "<build>"` to the reporter as
  each lease is made.
- Reads `LT_USERNAME` and `LT_ACCESS_KEY` from the run's environment and puts
  them only in the CDP URL: they never appear in a log line. A missing or
  blank one fails the lease with `LT_USERNAME and LT_ACCESS_KEY must be set`;
  in `worker` scope that ends the run before any test.
- Leaves a session a dead worker held to LambdaTest's idle timeout
  (`capabilities: { idleTimeout }`, in seconds), which ends it.
